# NOTIFY_CONTRACT.md — обмен AshCRM ↔ приложение уведомлений · версия **1.13** (2026-11-13)

Единственный источник правды для обмена между CRM (`crm-ashbyte`) и приложением уведомлений
(`crm-notify-windows-ashbyte`, в дальнейшем — **клиент**). Одна и та же копия лежит в обоих репозиториях:
`crm-ashbyte/docs/contracts/NOTIFY_CONTRACT.md` и `crm-notify-windows-ashbyte/docs/NOTIFY_CONTRACT.md`.

**Как менять.** Правка в CRM, которая касается клиента, начинается с этого файла: поднять версию, описать
изменение в §11, положить одинаковую копию в оба репозитория. Клиент дописывается по новой версии файла.
* **Минорная версия** (1.0 → 1.1) — только добавления: новые поля, виды карточек, кадры. Клиент обязан
  игнорировать незнакомые поля, `kind`, кадры и коды ошибок.
* **Старые версии не поддерживаются** (решение владельца 06.11): с новой версией контракта CRM и клиент обновляются
  вместе, CRM не держит ветки поведения для старых клиентов.
* **Мажорная версия** (1.x → 2.0) — несовместимо (поле убрано или поменяло смысл, другой вход). CRM сообщает
  версию в `hello.notify_contract` (§5.2); клиент с другой мажорной версией говорит «обновите приложение».
* Константы: CRM — `realtime.NotifyContract` (`core/internal/realtime/hub.go`); клиент — `app.Contract`
  (`internal/app/app.go`).

Подробности серверной реализации и решения владельца — `crm-ashbyte/docs/WINDOWS_NOTIFICATIONS_CRM_SPEC.md`.

## 1. Общее

* Адрес портала `<CRM>` — схема и хост (`https://crm.company.ru`), без пути. REST — `<CRM>/api/v1`, WebSocket —
  `wss://<host>/ws?v=1` (`ws://` для `http://`).
* `http://` — только для адресов локальной сети и этого компьютера (`localhost`, `127.0.0.0/8`, `10/8`,
  `172.16/12`, `192.168/16`): иначе ключи пошли бы по интернету открытым текстом.
* JSON UTF-8, время — RFC 3339 (`2026-10-30T12:00:00Z`), идентификаторы — UUID строкой.
* Ошибка REST — HTTP-статус и тело `{"error": {"code": "unauthorized", "message": "текст для человека"}}`.
  Коды: `bad_request` (400), `unauthorized` (401), `forbidden` (403), `not_found` (404), `conflict` (409),
  `validation` (422), `rate_limited` (429), `internal` (500); новые коды могут добавляться. Клиент показывает `message`, решения принимает по статусу.
* Клиент шлёт `User-Agent: AshCRM-Notify/<версия> (Windows)` — CRM пишет его в «Мои устройства» и аудит.

## 2. Вход через браузер (RFC 8252: loopback + PKCE)

Пароль, 2FA и сам вход остаются в CRM; клиент получает только ключи своей сессии.

1. Клиент создаёт `verifier` (32 случайных байта, base64url без `=`, 43 символа), `challenge =
   base64url(sha256(verifier))` (43 символа), `state` (8–128 символов `[A-Za-z0-9_-]`), слушает
   `http://127.0.0.1:<port>/callback` (`port` 1024–65535, только 127.0.0.1) и открывает в браузере:
   ```
   <CRM>/desktop-connect?challenge=<challenge>&state=<state>&port=<port>&device=<устройство>
   ```
2. Страница CRM (вход — если нужен) спрашивает «Подключить приложение AshCRM для Windows?» и по «Подключить»
   вызывает `POST /auth/desktop/authorize` (§3.1), затем открывает
   `http://127.0.0.1:<port>/callback?code=<code>&state=<state>`.
3. Клиент сверяет `state` (постоянное время сравнения), отвечает в браузер страницей «Готово» и меняет код:
   `POST /auth/desktop/token` (§3.2). Код живёт **2 минуты** и **сгорает при первой попытке**, удачной или нет.
4. Клиент ждёт возврата не дольше 5 минут; неверный `state` — вход отменён.

## 3. REST

### 3.1. `POST /auth/desktop/authorize` — вызывает страница CRM, не клиент
Требует обычный вход сотрудника в браузере. Тело `{"challenge": "<43>", "device": "DESKTOP-4F2K"}` →
`200 {"code": "<одноразовый код>"}`. `device` — произвольная строка, клиент присылает `<имя компьютера> / <пользователь Windows>`
(`TS01 / ivanov`); обрезается до 60 символов; пусто — «компьютер». Необязательное поле `app`: `"windows"` (по
умолчанию) или `"android"` — подключение приложения для Android ([`ANDROID_CONTRACT.md`](ANDROID_CONTRACT.md) §3); клиенту
Windows его передавать не нужно. `POST /auth/desktop/refresh` принимает и ключи приложения Android; необязательные
поля `device_key` (в `/token`), `device_key`/`device_ts`/`device_sig` (в `/refresh`) — только для него
(`ANDROID_CONTRACT.md` §3.3), клиент Windows их не передаёт.

### 3.2. `POST /auth/desktop/token` — без авторизации
```json
{"code": "…", "verifier": "…"}
```
→ `200 DesktopTokens`:
```json
{"access_token": "eyJ…", "expires_at": "2026-10-30T12:15:00Z",
 "refresh_token": "…", "refresh_expires_at": "2026-11-29T12:00:00Z",
 "user_id": "uuid", "session_id": "uuid"}
```
* Создаётся сессия вида `desktop` с именем `Windows · <device>`; прежняя сессия **с тем же именем** у этого
  сотрудника завершается (переустановка, потерянный ключ) — её сокет закрывается. Ключ — пара «сотрудник + устройство»:
  вход другого сотрудника с того же компьютера (терминальный сервер) чужую сессию не трогает.
* `401` — код неверен, устарел или уже использован, либо `verifier` не подходит. `403` — учётная запись или
  компания заблокирована.
* **Проверка портала**: `POST /auth/desktop/token` с телом `{}` у AshCRM 1.0 отвечает `401` с JSON-ошибкой;
  `404` с JSON-ошибкой — CRM старше, без приложения; другое — по адресу не AshCRM.

### 3.3. `POST /auth/desktop/refresh` — без авторизации
`{"refresh_token": "…"}` → `200 DesktopTokens` (новая пара). Ключ обновления **одноразовый**: сохранить новый
до использования. Повтор старого ключа завершает сессию (защита от кражи). `401` — сессия завершена (вышел,
завершена в «Мои устройства», заблокирован, 30 дней без обновлений): нужен новый вход. Ключ браузерной сессии
здесь не принимается (и ключ клиента — в обычном `/auth/refresh`). `409 conflict` — два обновления одновременно:
повторить через секунду с тем же ключом. Сеть и `5xx` — повторить позже, сессия не потеряна.

### 3.4. Ключ доступа
* `access_token` живёт **15 минут**, `refresh_token` — **30 дней** с последнего обновления.
* В REST ключ клиента открывает **только** `GET /me`, `POST /auth/logout`, с 1.10 `POST /uploads` и с 1.11
  `GET /desktop/stickers/<hash>.png`; остальное — `403`. Всё прочее идёт по WebSocket.
* `GET /desktop/stickers/<hash>.png` (с 1.11) — картинка стикера карточки (§5.3, поле `sticker`) → `200 image/png`:
  статичная PNG с прозрачным фоном, длинная сторона 192 px, пропорции стикера, до 256 КБ. По одному пути — всегда одна
  и та же картинка (`Cache-Control: max-age=31536000, immutable`), её SHA-256 = `hash`. Клиент хранит файл по `hash`
  и скачивает его один раз на компьютер. Нет такой картинки в компании — `404` (клиент показывает `body`). Ключом
  клиента другие вложения не читаются.
* `POST /uploads` (с 1.10) — файл ответа из карточки (§5.8): `multipart/form-data`, поле `file` → `201 Attachment`,
  нужен только `id` (его передают в `notify.reply` в `files`); `name`, `size` — для списка в карточке. Больше
  предела, запрещённый тип (SVG, подмена расширения) — `validation` с `message`. Загруженный и не отправленный файл
  CRM удаляет сама.
* `GET /me` (`Authorization: Bearer <access>`) → профиль; клиенту нужны `display_name` (имя в меню) и
  `tenant_name`. Остальные поля игнорировать.
* `POST /auth/logout` → `204`: завершает сессию клиента в CRM.

## 4. WebSocket `/ws?v=1`

### 4.1. Кадры
* Запрос клиента: `{"id": "w-1", "type": "<тип>", "data": {…}}`; ответ CRM:
  `{"re": "w-1", "ok": true, "data": {…}}` или `{"re": "w-1", "ok": false, "error": {"code": "…", "message": "…"}}`.
* Событие CRM: `{"type": "<тип>", "data": {…}}` (без `re`).
* Первый кадр клиента — `auth` (не позже 10 секунд), до ответа на него ничего не слать.

### 4.2. Что можно клиенту
Сокет с ключом клиента **получает только** `hello`, `ping` и `notify.*` и **может слать только** `auth`, `ping`,
`auth.refresh` и `notify.*`; остальное — ответ `forbidden`. Такой сокет не делает сотрудника «в сети».

### 4.3. Жизнь соединения
| Что | Как |
|---|---|
| `auth` | `{"token": "<access>"}` → ответ `ok`, затем событие `hello` (§5.2) |
| `ping` (CRM → клиент) | событие раз в 25 с, отвечать не нужно |
| `ping` (клиент → CRM) | запрос раз в 25 с, `{}`; сокет без кадров клиента 75 с закрывается |
| `auth.refresh` | `{"token": "<новый access>"}` → `ok`; раз в ~12 минут (до истечения 15) |
| после обрыва | переподключение с паузой 1 с → ×2 → до 60 с со случайной добавкой; после сна компьютера — сразу |

### 4.4. Коды закрытия
| Код | Значит | Клиент |
|---|---|---|
| 4001 | сессия завершена (вышел, «Мои устройства», повторное подключение того же сотрудника с того же устройства) | `refresh`; `401` → «войдите снова» |
| 4002 | ключ доступа истёк | `refresh`, переподключиться |
| 4003 | ключ не принят | `refresh`; `401` → «войдите снова» |
| 4008 | клиент не успевает читать | переподключиться |
| прочие | сеть, перезапуск CRM | переподключиться |

## 5. Уведомления

### 5.1. Порядок
1. После `auth` → `notify.snapshot` (запрос). Ответ — **полное текущее состояние**: клиент заменяет им всё,
   что знает (карточек, которых нет в снимке, больше нет).
2. События, пришедшие до ответа на снимок, применяются **после** него (иначе старый снимок отменит их).
3. Дальше — `notify.card`, `notify.clear`, `notify.sync` по мере событий. Доставка «хотя бы раз»: карточка
   определяется `key`, повтор её заменяет.

### 5.2. `hello` (событие)
`{"session_id": "uuid", "protocol": 1, "server_time": "…", "user_id": "uuid", "tenant_id": "uuid",
"notify_contract": "1.5"}`. Нет `notify_contract` — CRM 0.0.40, считать `1.0`.

### 5.3. Карточка `DesktopCard`
| Поле | Тип | Смысл |
|---|---|---|
| `key` | string | постоянный ключ (§5.4); новая карточка с тем же ключом **заменяет** прежнюю |
| `kind` | string | вид, как вид веб-пуша: `dm` `groups` `mine` `queue` `mentions` `tasks` `calendar` `alerts` `test`, с 1.3 — `call` (звонит клиент, §5.4), с 0.1.0 CRM — `policy` (Оргполитика: документ на подпись, напоминание), с 1.12 — `delivery` (модуль «Доставка»: заявки, водители, чат заявки); незнакомый — показывать как обычный |
| `title` | string | заголовок: чат, собеседник, клиент («Пётр»). С 1.13 без служебных слов: у очереди — просто клиент (не «Новый клиент: Пётр» / «Пётр — беседа в очереди»), у переданной беседы — клиент, кто передал — в `body`; у пропущенного звонка — клиент, в `body` «15:04 · ждал 12 с · Отдел продаж»; откуда событие — поле `category` |
| `body` | string | текст (последнее сообщение, «Иван: …»); при «Пуш без текста» в CRM — «Новое сообщение» или пусто |
| `url` | string | **путь** в CRM (`/team/<chat>`, `/my/<conversation>`, `/queue/<conversation>`, ссылка уведомления); клиент открывает только `<CRM> + url`, путь должен начинаться с одного `/` |
| `count` | int | сообщений в строке чата (≥ 1); 0 — не применимо |
| `sound` | string | `client` — сообщение клиента или новая беседа; с 1.12 `delivery` — всё о доставке (свой звук: водители и сотрудники, получающие уведомления доставки); `other` — остальное; незнакомое — как `other` |
| `at` | time | время события |
| `mention` | bool | в чате упомянули сотрудника |
| `call` | object? | с 1.4, только у вида `call`: `{"state": "ringing" \| "talking"}` — звонит / идёт разговор у этого сотрудника |
| `actions` | Action[]? | с 1.4: готовые кнопки карточки; клиент показывает их как есть, в данном порядке |
| `from` | string? | с 1.10, только в беседе с клиентом (`chat-` беседы, `queue-`): `client` — последним написал клиент, `staff` — коллега внутри беседы (внутренняя заметка, клиент её не видит). В других чатах поля нет |
| `alert` | bool | с 1.12: **заметная** карточка — показать ярко (красным) и со звуком погромче: пинг диспетчера, «Не удалось» на точке, «Срок прошёл», срочная заявка, «Поставили раньше заявки в работе», «Водитель снят». Нет поля — `false` |
| `reply` | Reply? | с 1.10: на карточку можно ответить прямо сейчас (§5.8), с теми же правами, что в CRM. Нет поля — нет кнопки «Ответить» |
| `category` | string? | с 1.13: **откуда событие** — значок и цвет карточки (единый стиль, `docs/NOTIFICATION_STYLE_TZ.md`): `call_missed` пропущенный звонок, `call_incoming` звонок (карточки вида `call`), `queue` клиент в «Ожидают», `client_message` сообщение клиента в беседе, `colleague_direct` личное сообщение коллеги, `group_message` группа сотрудников, `mention` упоминание, `conversation_assigned` беседу передали, `task`, `calendar`, `policy`, `delivery`, `alert` — системное предупреждение. Значки и цвета — §5.3.1. Нет поля или незнакомое значение — значок приложения, цвет по `kind` как раньше |
| `sticker` | Sticker? | с 1.11, у карточек сообщений (`chat-`, `queue-`): последнее сообщение — **стикер из наборов компании** (репозитории стикеров CRM; отправил сотрудник или CRM узнала стикер клиента как свой). `{"code": "<pack>/<id>", "hash": "<sha256 png>", "url": "/api/v1/desktop/stickers/<hash>.png"}`; без `hash` и `url` — картинки нет, показывать `body`. Чужие стикеры, не последнее сообщение и «Пуш без текста» — поля нет, `body` = «Стикер» как раньше |

`Action`: `{"id": "client" | "message" | "check", "title": "…", "url": "/…", "primary": true}` — `title` — текст
кнопки, `url` — **путь** в CRM (клиент открывает только `<CRM> + url`, §6, может быть с `?…`), `primary` — главная из
кнопок `message` (остальные `message` — в меню рядом с ней). Незнакомый `id` — показывать как обычную кнопку.
Нажатие кнопки карточку не убирает.

`Reply` (с 1.10): `{"modes": [{"id": "…", "title": "…"}], "takes": true, "files": {"max_mb": 40, "max_count": 10}}`.
* `modes` — куда можно ответить, **первый — по умолчанию**. В беседе с клиентом: `client` «Клиенту в WhatsApp»
  (канал ответа по умолчанию, как в CRM; нет канала, куда клиенту можно написать, — режима нет) и `internal` «Внутри
  беседы» (клиент не увидит); на сообщение клиента первым идёт `client`, на внутреннюю заметку — `internal`. В личном
  чате, группе, чате задачи или встречи — один режим `chat` («Ответ: Мария Иванова», «Ответ в группу «Продажи»», «Ответ
  в чат задачи», с 1.12 — «Ответ в чат заявки»): переключатель не показывать. Незнакомый `id` — показывать как есть по `title`.
* `takes: true` — только у `queue-`: ответ **берёт беседу** на сотрудника (ярко пометить «Новая беседа»). Приходит
  только оператору на смене и не в чужом окне закреплённого клиента: оператор не на смене карточек «Ожидают» не
  получает вовсе.
* `files` — можно приложить файлы (до `max_count`, каждый до `max_mb` МБ, `docs/OUTBOUND_ATTACHMENTS.md`); нет поля — без
  скрепки.
* `reply` есть у `chat-` (личный чат, группа без ограничения «пишут выбранные», чат задачи или встречи, с 1.12 — чат
  заявки доставки, пока заявка не в архиве; беседа с клиентом в работе, в которой сотрудник участвует) и `queue-` (с `takes`). У `alert-`, звонков, задач, встреч, каналов
  — нет.

Пример:
```json
{"key": "chat-0193…", "kind": "dm", "category": "colleague_direct", "title": "Мария Иванова", "body": "Привет!",
 "url": "/team/0193…", "count": 2, "sound": "other", "at": "2026-10-30T12:00:00Z", "mention": false}
```

#### 5.3.1. Значки и цвета категорий (с 1.13)

Значок слева на карточке и цветная полоса — по `category`. Значки — формы набора **lucide** (как в левой панели CRM),
белый контур на круге цвета категории; PNG 192×192 тех же значков лежат в CRM: `GET /icons/notify/<category>.png`
(без авторизации, статический файл PWA) — можно взять их или нарисовать те же формы у себя. Служебных слов
(«Пропущенный звонок:», «Новый клиент:», «— беседа в очереди») в `title` нет — их заменяет значок.

### 5.4. Ключи
| `key` | Карточка | Исчезает (`notify.sync` / `notify.clear`) |
|---|---|---|
| `chat-<chat_id>` | непрочитанное в чате: личном, группе, чате задачи или встречи, беседе с клиентом; упоминание | чат прочитан до последнего сообщения |
| `queue-<conversation_id>` | новая беседа в очереди | беседа ушла из «Ожидают» |
| `alert-<conversation_id>` | «никого нет на смене» (руководителям) | беседа ушла из «Ожидают» |
| `task-<task_id>`, `event-<event_id>`, `channel-<channel_id>` | задача, встреча, тревога канала | уведомления по ней прочитаны |
| `delivery-<request_id>` | с 1.12: заявка доставки — новая, принята, водитель назначен, точка выполнена / «Не удалось», доставлено, пинг, очерёдность, сроки (вид `delivery`, звук `delivery`, `alert` у заметных); `url` — `/delivery/<номер>`. Сообщение **чата заявки** — обычный ключ `chat-<chat_id>` вида `delivery`, `url` — `/delivery/<номер>?chat=1` (чат живёт внутри заявки, в списке чатов CRM его нет) | уведомления по заявке прочитаны (`notify.read` — только строки колокольчика, заявка не меняется) |
| `test-<uuid>` | проверка из «Настройки → Уведомления» (вид `test`, с 1.1) | «Прочитано» или следующий `notify.sync`; в снимок не входит |
| `ring-<call_id>` | с 1.7 не приходит по личным звонкам и звонкам «Спама» (`CALLS_RULES.md` R-IN4, R-IN9). С 1.3: **звонит клиент** (вид `call`, звук `client`, `call.state` `ringing`) — тем, у кого сейчас звонит телефон АТС МегаФон: заголовок «Звонит: Имя - Организация» или «Звонит: Новый номер», текст — номер клиента → номер компании / группа, `url` — `/c/<chat_id>` (пусто, если беседы нет). С 1.4 **ответившему** — та же карточка (тот же ключ, `count` тот же — без звука) «Разговор: Имя - Организация» / «Разговор: новый номер», `call.state` `talking` и кнопки (ниже); при переводе карточка переходит к новому сотруднику | `ringing`: `notify.clear` при ответе (тем, кто не ответил) или конце звонка; в снимок не входит — клиент держит её не дольше 3 минут. `talking`: `notify.clear` в конце разговора; **входит в снимок и `notify.sync`**, пока разговор идёт (не дольше 4 часов) — пропавшая из снимка убирается, предела времени нет. `notify.read` не нужен. Показывать сразу и заметно, без накопления; «Пропустить» убирает карточку только у себя |

С 1.7 текст — «время · кому звонили · ждал N с · канал»; **личный** пропущенный (схема звонков `CALLS_RULES.md` R-IN9) — только его владельцу, вид `dm`, `url` — `/calls/<call_id>`, приходит и вне рабочего дня | перезвонили клиенту или отметили «Обработан» (`notify.sync`); в снимке есть, вне рабочего дня — нет, как остальные `queue`. С 1.5 `notify.read` по нему читает строку колокольчика, звонок остаётся необработанным |

Кнопки «Разговора» (1.4): `client` «Карточка клиента» → `/contacts/<contact_id>` (у нового номера — карточка «из
звонка», там «Добавить в контакты»); `message` «Написать в <канал>» → `/c/<chat_id>?via=<endpoint_id>` — по одной на
мессенджер, в котором клиент уже известен, `primary` — канал ответа по умолчанию, он первый; `check` «Проверить
мессенджеры» → `/contacts/<contact_id>?check=1` — клиент говорит, куда ему писать, карточка открывается на кнопках
мессенджеров, сотрудник проверяет номер в названном (сама CRM номер при звонке не проверяет: лимит проверок и риск бана
номеров). Без карточки клиента кнопок нет.

Незнакомый префикс ключа — показывать, `notify.read` по нему CRM может отклонить.

### 5.5. Кадры
| Кадр | Направление | Данные |
|---|---|---|
| `notify.snapshot` | запрос → ответ | `{"cards": DesktopCard[], "total": int}` — до **20** самых новых карточек за последние **24 часа**; `total` — сколько их всего («ещё N — откройте CRM»). С 1.4 первыми идут идущие разговоры сотрудника (`ring-…`, `talking`), сверх 20 |
| `notify.card` | событие | `DesktopCard` — новая или обновлённая карточка; **звук — только по нему** (и если `count` вырос) |
| `notify.clear` | событие | `{"keys": ["…"]}` — убрать карточки |
| `notify.sync` | событие | как ответ `notify.snapshot`; приходит после любого прочтения у сотрудника (не чаще раза в 300 мс): заменить состояние — исчезнувшие карточки убрать |
| `notify.activity` | запрос | с 1.2: `{"active": true}` → `{"ok": true}` — пользователь работает за компьютером (§5.7). Статус сотрудника для коллег не меняет |
| `notify.read` | запрос | `{"key": "…"}` → `{"ok": true}` — «Прочитано»: чат читается до последнего сообщения, уведомления задачи/встречи/канала отмечаются; для `queue-`/`alert-`/`missedcall-` сама работа не меняется (беседа остаётся в «Ожидают», звонок — необработанным). С 1.5 по любому ключу читаются и строки колокольчика этого сотрудника с этим ключом — как нажатие на строку в колокольчике. Все устройства сотрудника получают `notify.clear` и `notify.sync`. Неизвестный ключ — ошибка `validation` |
| `notify.reply` | запрос | с 1.10: `{"key": "…", "mode": "client", "text": "…", "files": ["<id из /uploads>"], "client_id": "<uuid>"}` → `{"ok": true}` — ответ из карточки (§5.8) |
| `notify.read_all` | запрос | с 1.5: `{"before": "<RFC 3339>"}` → `{"ok": true, "read": int}` — «Прочитать все»: всё непрочитанное в колокольчике сотрудника, пришедшее не позже `before` (момент нажатия; время в будущем считается текущим), — как `notify.read` по каждой строке: чаты читаются до сообщения своей строки, задачи, встречи, каналы — вместе со строками. Карточка, в которую после `before` пришло новое (например, ещё одно сообщение в тот же чат), остаётся непрочитанной целиком и приходит заново. `read` — сколько строк прочитано. Затем `notify.clear` с ключами прочитанного и один `notify.sync`. Без `before` — ошибка `bad_request` |

### 5.6. Какие события становятся карточками
С 1.2 снимок и карточки строятся из единого списка уведомлений CRM (колокольчика): одни правила для всех каналов, с
личными настройками сотрудника и заглушёнными чатами. Выключатель «Приложение Windows» в настройках сотрудника
(`channel_desktop`) останавливает карточки и делает снимок пустым. Карточки нет, если сотрудник прямо сейчас смотрит на
этот чат в CRM: вкладка видна, окно в фокусе, действие за последнюю минуту. Если он отошёл и чат остался открытым,
карточка приходит. Пока клиент подключён, CRM не шлёт веб-пуш в браузеры компьютеров (настройка
`desktop_mutes_browser`, по умолчанию включена).

С 1.2 карточка `alert-<conversation_id>` входит в снимок. Прочитанная в колокольчике строка исчезает и из снимка, даже
если сам чат ещё не прочитан. Непрочитанное, накопленное до обновления CRM, в снимок не входит.

**Рабочий день (с 1.6, раньше — 1.1).** Рабочий день есть у каждого сотрудника. Пока он не начат, приходят и
попадают в снимок только: `dm`; `mentions` (и `@все`, и упоминание в чате клиента); `calendar` — только напоминание о
встрече; `groups` — из групп, где выключено «Уведомлять только работающих» (по умолчанию включено). Остальное
(`queue`, `mine`, `tasks`, `policy`, `alerts`, прочие `calendar`, группы «только работающих», с 1.12 — всё `delivery`,
включая упоминания в чате заявки) копится в колокольчике CRM без карточек. Начало дня: снимок `notify.sync` с накопленным без звука, затем по одной `notify.card` на источник —
на чат «N новых сообщений», «Задачи», «Оргполитика: документов на подпись N», «Пропущенные звонки: N» (времена
звонков в тексте), «Ожидают». Ключ такой карточки — ключ самой новой строки источника (обычные префиксы §5.4).
Конец дня: снимок без того, что ждёт рабочего дня. Входящий звонок (`ring-`) не на рабочем дне не приходит.

**Проверка (с 1.1).** Кнопка «Проверить уведомления» в CRM присылает подключённому клиенту `notify.card` с ключом
`test-<uuid>` мимо всех правил (рабочий день, настройки сотрудника). Ключ новый при каждой проверке. Клиент показывает
карточку как обычную; менять в нём ничего не нужно.

### 5.7. Активность пользователя (с 1.2)
CRM не присылает пуш на телефон, пока сотрудник работает за компьютером. Браузер видит только действия в окне CRM,
поэтому клиент может сообщить о любых действиях пользователя в своей сессии Windows.
* Клиент шлёт `notify.activity` после каждого подключения и при смене состояния. `active: true` — ввод был в последнюю
  **1 минуту**, `false` — ввода не было.
* Подключённый клиент, приславший кадр, важнее вкладок CRM: `false` запускает пуши на телефон, даже если вкладка ещё
  «в сети». Статус сотрудника для коллег от этого не меняется.
* Состояние живёт, пока жив сокет: обрыв или закрытие сокета снимает признак.
* Кадр необязателен: без него телефон учитывает только вкладки CRM.
* Карточек и звука кадр не меняет: клиент получает их сразу при любом значении.

### 5.8. Ответ из карточки (с 1.10)
* Сообщение уходит от имени сотрудника, как если бы он написал его в CRM: `client` — клиенту в канал из `title`
  режима, `internal` — внутренняя заметка в беседе, `chat` — в чат. `text` — обычный текст, может быть пустым, если есть
  файлы; ни текста, ни файлов или текст длиннее 10 000 символов — `validation`.
* `queue-` с `takes`: беседа сначала берётся на сотрудника («Взять»), затем уходит ответ. Её уже взял другой —
  `conflict` с `message`, ничего не отправлено. Взятая беседа уходит из «Ожидают» у всех, как в CRM.
* `client_id` — ключ повтора: тот же запрос ещё раз (обрыв связи) второго сообщения не создаёт; повтор ответа на
  `queue-`, который беседу уже взял, отправляет то же сообщение в уже свою беседу.
* Затем чат читается до последнего сообщения, как `notify.read`: строки колокольчика, `notify.clear` и `notify.sync`
  на все устройства (карточка `queue-` уходит вместе с беседой).
* Нельзя ответить (нет прав, беседа закрыта, режим недоступен, например клиенту больше нельзя писать) — `forbidden`
  или `conflict` с `message` для человека: показывать как есть, текст и файлы не терять.
* Ответ из приложения не делает сотрудника «в сети».

## 6. Требования к клиенту (безопасность)
* Ключ обновления хранить зашифрованным для пользователя ОС (Windows — DPAPI); ключи не писать в журналы.
* `state` сверять; слушать только `127.0.0.1`; страница возврата не должна показывать код.
* Открывать в браузере **только** `<CRM> + url` карточки (путь), никакие абсолютные адреса от сервера.
* Обновления самого клиента — только из релизов его репозитория с проверкой SHA-256.
* Незнакомые поля, виды, ключи и кадры — игнорировать (минорные версии контракта).
